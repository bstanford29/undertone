Undertone: local dictation, kept on the Mac

Hold a key, talk, let go. Clean text lands in whatever app has focus. Whisper and a local model do the work. The clipboard is never touched. Meetings get transcribed and summarized into Obsidian.

What we proved today

Cloud dictation services do this work on a server. This runs entirely on this machine. Speech-to-text is whisper-large-v3-turbo through MLX. Cleanup is an Ollama model. Both were measured on real dictation with the model kept warm, which is how the app will run them.

The target end-to-end latency is under one second. Our fast tier lands near 900 ms once whisper and the model are both warm. That is the number to beat in Phase 2.

Shape of the app

Two processes. A small Swift menu bar app owns everything that needs the operating system: the hold key, the microphone, the on-screen pill, text insertion, and system audio for meetings. A Python engine owns the models. They talk over a local Unix socket. The prototype being built right now is the engine plus a temporary Python hotkey listener, so the loop can be proven before any Swift is written.

Menu bar app
Swift and SwiftUI. Global key tap, microphone, pill overlay, sound cues, AX insertion, ScreenCaptureKit audio for meetings, settings window.
Engine
Python 3.12 with mlx_whisper in-process, Ollama over HTTP, SQLite history, YAML dictionary. Runs as a launchd agent so models stay warm.
Models
whisper-large-v3-turbo for speech. qwen3.5 as the default cleaner, gemma4:31b for high cleanup, Command Mode, and meeting summaries. Both already installed.
Permissions
Microphone, Accessibility, Input Monitoring. Screen and system audio recording for meetings. Nothing else.

The clipboard rule

Undertone never writes to the clipboard during dictation. Not even save-and-restore. Whatever you copied before you spoke is still there after.

Most dictation apps paste because it is easy. We do not. Insertion climbs this ladder and stops at the first rung that works.

1
Accessibility API. Ask macOS for the focused text element and set its selected text to the new string. This inserts at the caret or replaces a selection. Works in native apps and most Electron apps.
2
Synthesized keystrokes. Post Unicode keyboard events in short chunks. Slower for long text, but it works anywhere that takes typing, including terminals like Ghostty.
off
Paste with restore. Exists in the code behind a config flag for one stubborn app someday. Off by default and logged loudly when used.

How the dictionary works

Each dictation carries context: the window's visible text before insertion, and how far the inserted text was later edited. A well-used dictionary ends up with most of its entries learned rather than typed by hand.

Three feeds into one list

  1. Manual. undertone dictionary add "Northwind", or the settings window. Replacements live here too: "btw" to "by the way", "my email" to the address.
  2. Edit watching. After insertion, watch the focused field for about 20 seconds. If you change a word the model produced, and the new word is capitalized or not in a common-word list, propose it. One confirmation adds it.
  3. Screen harvest. Before transcribing, read proper nouns from the focused window through Accessibility and add them to the whisper vocabulary prompt for that one dictation. Names of people in a chat thread get spelled right without ever being saved.

Where it is applied

Whisper takes the terms as its initial prompt, capped near 180 tokens and ordered by recent use. The cleaner gets the same terms in its system prompt. Replacements run as plain string substitution after cleanup, so they never depend on the model.

Meetings

Undertone captures the Mac's audio without a bot joining the call, using ScreenCaptureKit for system audio on macOS 13 and later. The microphone is recorded as a second channel. That split gives speaker labels for free: mic is you, system audio is everyone else. Finer diarization can come later with a local speaker-embedding model.

Capture
Two channels at 16 kHz. Voice activity detection gates chunks so whisper never sees silence, which is where it hallucinates.
Live transcript
Chunks of about 10 seconds. Output as NDJSON lines with id, timestamp, text, speaker.
After the meeting
gemma4:31b writes a summary, decisions, and to-dos. One markdown note lands in the Obsidian vault with the transcript folded below.
Storage
Audio and transcript under ~/.undertone/meetings/<id>/. Nothing uploaded.

Evaluation approach

Cleanup quality is graded against a private set of the author's own dictations: raw text, the cleaned result, and later edits. It is not included in this repo; anyone can build their own from their own dictation history. It is what makes the numbers in this plan and in bench/RESULTS.md real rather than synthetic.

bench/eval_cleanup.py reads pairs from this private set and scores our cleanup output against the earlier reference. The set stays out of version control; only IDs and metrics ever leave it.

Risks and open calls

  • AX insertion in Electron. Codex and Claude Desktop are Electron. Some Electron fields reject the selected-text write. Phase 1 tests this first. If it fails, keystrokes are the path for those apps and we measure the speed.
  • The fn key. Capturing fn as a hold key needs a low-level event tap and Input Monitoring permission. The prototype uses F13 to avoid this. The Swift app takes fn on.
  • GPU contention with other local model servers. If something else on the Mac already serves a model through MLX, Ollama unloads models after five minutes idle by default. Undertone sets keep-alive so the cleaner stays warm; a machine with enough unified memory leaves room for both.
  • Whisper on silence. Whisper invents text when handed silence. A voice activity gate before transcription, and a minimum recording length, prevent it.
  • Speed. The fast tier is around 900 ms against a target under one second. Two ideas if that feels slow: stream whisper while the key is still held so only cleanup runs on release, and skip the model for very short dictations under six words.
  • Diarization. Mic versus system audio covers most calls. True multi-speaker labels on the far side need a local embedding model and is a later addition.
